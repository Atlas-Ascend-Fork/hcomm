# 检视规范：异步与资源生命周期

本仓的资源都带生命周期——异步任务、回调、设备内存、通信域实例、动态插件。这类缺陷通常不在被改动的那一行，要沿「谁创建、谁持有、谁在何时使用、谁释放」读完整链路。适用于 `src/`、`experimental/`、`test/`、`examples/` 等全部 C/C++ 代码。

各节标题标注的级别是该节**硬性条目**的默认级别；条目本身标注「不报」「可从宽」或属经验建议的，按 MEDIUM/LOW 报，不按标题级别阻塞合入。

## 异步任务与回调（HIGH）

回调可能在捕获对象析构之后才执行，这是这类问题的主要来源。

- **回调执行时捕获对象必须存活**：回调可能晚于捕获对象析构执行时，须在析构前反注册/取消；持有方与捕获对象同为进程级生命周期、或回调不捕获任何对象（自由函数、无上下文指针）时无需注销
- **捕获 `this`/引用/裸指针时核对调用时机**：同步回调不报；异步回调（线程池、任务队列、设备中断、DFX 回调）要求捕获对象的生命周期覆盖到回调执行完成（`shared_ptr`/`weak_ptr` 守卫、join 后释放等）
- **opaque 指针（`userData` 等）同样算捕获**：注册回调时传入的上下文指针，其对象必须在回调有效期内存活
- **提交即返回要能证明对象存活**：任务按值拷贝对象本体（拷贝的必须是对象本身而非指针/引用）、或按 `shared_ptr`/`weak_ptr` 持有所有权，或提供 wait/join/同步取消（返回时任务已确认不再使用捕获对象）路径都算合规；按值捕获裸指针/引用不延长所指对象的生命周期，仍按「捕获裸指针」逐项核对捕获对象存活期；仅有 best-effort 取消标志、或任务引用调用方对象（含栈对象）又没有任何等待路径时仍报 HIGH
- **锁内回调与回调重入**：回调持锁执行、或回调里再回调同一对象（re-entrancy）时核查死锁与状态破坏

## 资源所有权（HIGH）

每个资源必须只有一个明确所有者，且所有权在接口上有约定。

- **返回裸指针/句柄的接口写清归属**：谁负责释放、是否转移所有权；成员、容器、出参之间移动所有权时不能出现「双方都以为对方释放」
- **move 之后源对象状态明确**：移出后不得再使用；容器插入失败的回滚路径不得留下半转移状态
- **释放与使用者的生命周期对齐**：释放前确认无并发使用者；优先 RAII，不依赖手工配对

## Host / Device 内存（HIGH）

Host 与 Device 内存的生命周期不同步，是最容易出问题的区域。

- **申请释放配对**：Device 内存（`aclrtMalloc` 等）只能由对应接口释放，不能在 Host 侧 `free`；错误路径同样要释放
- **异步访问期间不得释放**：Host 内存被 Device（DMA/HCCS 读写）异步使用时，释放必须发生在操作完成之后（stream 同步、event 等待），否则悬垂
- **注册类内存注销前确认无在途硬件访问**：注册给网卡/HCCS 的地址段（如 `roce_reged_mem_mgr` 管理的内存）在注销前不得仍有硬件在读写
- **大小与对齐**：Device 内存按接口要求对齐；Host/Device 指针混用（把 device 指针当 host 用）命中即报

## 多通信域与多设备实例（HIGH）

同一进程内会有多个通信域、多个 device 实例，状态必须按实例隔离。

- **per-instance 状态不挂进程级单例**：多通信域/多设备场景的实例状态挂在全局单例上会相互污染；确需进程级单例按 coding-and-security 的全局状态规则评审，评审通过的不重复报
- **索引键正确**：按实例索引的资源（channel、stream、上下文、内存注册）确认用对 `deviceId`/`rankId`/`commId`，不混用
- **析构顺序**：通信域析构时其下资源先释放；同一通信域的并发创建/销毁须有同步

## Stream / Event / Notify（HIGH）

这些对象跨线程共享并带隐式队列语义，缺失同步表现为随机失败。

- **同 stream 串行、跨 stream 要 event 同步**：核查依赖关系，不因「本地测试通过」放过随机问题
- **句柄并发读写需锁或原子**；销毁前确认无在途操作（同步点或引用计数）
- **等待必须有出口**：Notify/event 等待要确认对端必然触发或有超时，无超时的永久等待会导致挂死
- 优先复用仓内既有的线程/流封装，不直接裸调底层接口

## 插件动态加载与卸载（HIGH）

插件（如 `src/base_comm/primitives/api_c_adpt/nic_plugin/` 的 `LoadAllNicPlugins`）带来「函数指针与 .so 同生命周期」的约束。

- **`dlclose` 后不得再调用插件函数**，也不得保留指向插件代码的回调/函数指针（`soHandle` 与全部导出符号同生命周期）
- **卸载前确认插件创建的对象已全部销毁**（channel、endpoint 等）
- **加载失败与符号缺失走错误路径**：`dlopen`/`dlsym` 结果必须判空，不能解引用空函数指针
- **插件与通信域生命周期解耦是既定设计**：插件一次性加载（`LoadAllNicPlugins` 走 `call_once`），成功加载的句柄不卸载、仅加载失败路径 `dlclose`（不随单个通信域销毁而卸载），不按「通信域销毁必须卸载插件」报
- 插件回调进主流程注意重入，异常不得穿过 C 接口边界
